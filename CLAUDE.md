# Terran Vanguard — working rules

A vertical shoot'em up set in 2185 (see [design/README.md](design/README.md)). The project is
currently in the **design phase**: there is no game code yet. The `design/` tree is a *living
documentation* that is the single source of truth for the game and doubles as the
implementation backlog (every README is a ticket). Keep it up to date in the same change as
the work it describes.

## The design tree

- Organised **by domain**: `art-direction/`, `story/`, `world/`, `campaign/`, `enemies/`,
  `player/`, `systems/`, `ui/`, `audio/`, plus `concept-rounds/` (open choices for the user).
- **Every directory has a `README.md`** that describes the directory's contents, including
  every subdirectory. Only `concept/` directories are exempt (see below).
- **No duplication.** A level references the enemies, music, settings and weapons it uses by
  relative link; the definition lives in exactly one place.
- **A part gets its own directory once it leaves `idea` status.** Until then it is a row in the
  parent README's roster table. When promoting a row, create the directory + README and replace
  the roster row by a Contents row.
- Naming: lowercase kebab-case. Acts: `act-N-slug`. Levels: `level-NN-slug` with **global**
  numbering `01`–`50` (not per act). Enemies/weapons: `slug` (e.g. `swarmer-drone`).
- The design is **engine-agnostic** until a tech stack is chosen (that decision will get a
  `design/tech/` section). Describe behaviour, numbers and assets, not engine APIs.

## README format

Every README starts with frontmatter:

```yaml
---
title: Swarmer drone
design: idea | draft | review | approved
implementation: n/a | not-started | in-progress | done
art: n/a | none | proposed | chosen | final
depends-on: [../../player/weapons]   # optional, relative paths
updated: 2026-09-30                  # date of last meaningful change
---
```

Status meaning:
- `design`: `idea` (one-liner) → `draft` (written, not reviewed) → `review` (waiting for the
  user) → `approved` (user signed off). Only the user approves; never set `approved` yourself.
- `implementation`: `n/a` for pure index/lore docs; otherwise `not-started` → `in-progress` → `done`.
- `art`: `n/a` if the part has no visual/audio assets; `none` → `proposed` (variants in a concept
  round) → `chosen` (user picked a variant; still a mockup) → `final` (production asset).

Standard sections, in this order (omit the ones that do not apply):

1. **Summary** – two or three sentences.
2. **Contents** – a table of the subdirectories, exactly in this form, kept in sync with the
   children's frontmatter (the checker verifies it):
   `| Part | Summary | Design | Impl | Art |` with the Part cell a link `[name](name/README.md)`.
   Items still in `idea` status go in a separate **Roster** table (no link, no status columns
   required beyond `Design`).
3. **Design** – the actual design: behaviour, numbers, rules, references to other parts.
4. **Concept art** – table `| File | What | Status |` listing every file in `concept/`
   (status: `proposed`, `chosen`, `rejected`). Link the prompts file.
5. **Implementation** – acceptance criteria as a `- [ ]` checklist. This is the ticket.
6. **Open questions** – things the user still has to decide.
7. **Decisions** – dated log (`- 2026-09-30: ...`) of choices made, incl. rejected variants and why.

When you change a part: update its `updated` date and statuses, then update the row for it in
the parent's Contents table. Run the checker afterwards.

## Concept art

- The user chooses; Claude proposes. Never replace or delete a `chosen`/`final` asset without
  the user's explicit choice.
- Proposals go in the part's `concept/` directory, named `<subject>-r<RR>-<variant>.<ext>`
  (e.g. `player-ship-r01-b.png`, round 01, variant b).
- Every image item gets an AI-generator prompt / artist brief in `concept/prompts.md`
  (same subject name as heading). Audio items get a brief there too.
- After the user chooses: the chosen file stays in `concept/`, rejected files move to
  `concept/rejected/`, the Concept art table and the Decisions log record the outcome and why.
- Mockups generated by code must be reproducible: the generator lives in `tools/concept/` and
  its path is mentioned in `prompts.md`. Do not hand-edit generated files.
- A batch of proposals is a **concept round**: `design/concept-rounds/round-RR/` holds a
  `README.md` (the list of choices the user has to make) and an `index.html` review board that
  shows all images side by side and plays the audio (relative links into the design tree).
  Update `design/concept-rounds/README.md` when a round opens or closes.
- Binary files (png, gif, wav, ogg, …) are stored in Git LFS (`.gitattributes`).
- **Third-party assets** (e.g. sound effects from Freesound, OpenGameArt, Kenney): the GitHub
  repository is public, so only **CC0** or **CC-BY** (any version) assets are allowed — never
  licences that forbid redistributing the raw files (Pixabay, Sonniss GDC bundles, "royalty
  free" store packs) or non-commercial ones (CC-BY-NC). Every third-party file is recorded in
  [CREDITS.md](CREDITS.md) with file path, title, author, source URL, licence and what was
  changed; the part's `concept/prompts.md` links the source too. CC-BY items must later appear
  on the in-game credits screen.

## Art and game fundamentals (decided)

Late-90s **pre-rendered CGI sprite** look · 16:9 screen with a portrait play field and HUD side
panels · single-player · ~50 levels in 7 linear acts by setting · Tyrian-style loadout (front,
rear, left/right wing mounts, generator, shield, armour, special) · regenerating shield plus
non-regenerating armour; at zero armour the level is retried and that attempt's credits are
lost · difficulties easy/medium/hard · story: alien invasion with a mid-campaign twist, serious
tone with pulp edges, told through briefings and in-level radio chatter. Details live in the
design tree; this list is only a reminder.

## Tools

- `python3 tools/check_docs.py` – validates the design tree (README presence, frontmatter,
  Contents tables in sync with children, concept files listed, relative links resolve).
  **Run it after every documentation change** and fix what it reports.
  `--fix` first syncs the Contents status cells from the children's frontmatter (bottom-up
  order matters: run it twice when a change ripples up more than one level).
- `tools/concept/` – reproducible generators for concept mockups (Python 3 + PIL + numpy,
  ffmpeg for audio/GIF encoding). Each script documents its outputs at the top.

## Git

- Ask before committing or pushing. Binaries must go through LFS (`git lfs ls-files` to check).
